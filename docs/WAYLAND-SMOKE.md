## Correction and held-key finding (8:11)
- CORRECTION of the clipboard caveat above: the failed copy "without a prior key press" was a test artefact. The data device is only created when the seat reports a keyboard (new_capability), and the headless sway had no keyboard until wtype created one. With a keyboard capability present (tools/sway_ptr_cap.sh: `wtype -s 100` creates and drops a virtual keyboard, then a pointer click), a click copies the exact bubble text on both builds with NO key press. A trial fix storing the pointer-press serial changed nothing and was reverted. Remaining real edge case, not tested: a seat whose keyboard is hot-plugged after start creates the data device only then (no copy until a keyboard appears); a seat that never has a keyboard cannot copy at all.
- Held-key repeat: tools/sway_rep.sh holds a virtual key for 2 s (`wtype -P a -s 2000 -p a`). BOTH builds show a single "a" (no repeat). Cause by source: Pawline calls get_keyboard(..., None) instead of get_keyboard_with_repeat, so no client-side repeat exists on Wayland (the compositor does not repeat for clients). This is a real Wayland gap in baseline and migration (holding Backspace or an arrow key does not repeat; X11 is repeated by the X server). Therefore the migration's new repeat_key handler is never called, and the repeat path remains untested. ## Held-key repeat implemented on the baseline (8:13)
Baseline (sctk 0.19.2) now uses get_keyboard_with_repeat with the app's calloop handle (field `lh`), so a held key repeats at the compositor-announced rate and delay. Sandbox sway, release build, tools/sway_rep.sh (`wtype -P a -s 2000 -p a`): the input shows "x" plus 26 "a" characters after a 2 s hold (before: a single "a"); repeat stops on release. Image /tmp/swr_c_fixrep.png. One run, author-written, sway only. The migrated branch (sctk 0.21) does NOT have this change yet: its repeat goes through KeyboardHandler::repeat_key and needs the equivalent 0.21 call, then the same script.
